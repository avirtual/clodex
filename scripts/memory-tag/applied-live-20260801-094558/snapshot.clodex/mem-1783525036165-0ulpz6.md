Contrarian review of peer+stream cross-laptop attach (2026-07-10, verdict approve-with-conditions) — amends the multi-host parked note's "phase 1" shape. Conditions adopted: (1) passive attach NEVER mutates owner PTY state — owner size canonical, viewer letterboxes; (2) interactive control = explicit "take control" mode (not focus-implicit), and control mode is what grants resize authority — clean fit for the real use case (B unattended while at A); (3) replay is best-effort scrollback only, protocol disclaims exact terminal-state restoration; on reconnect, reset viewer xterm and attach from live stream boundary (raw-byte replay mid-alternate-screen corrupts xterm); (4) renderer seam approved only as thin adapter (listSessions/subscribeOutput/sendInput/resize/status) — reconnect/buffering/protocol logic stays out of renderer.js; (5) forwarded control port = shell-equivalent; split read-only endpoints from control endpoints, add per-connection ephemeral capability tokens (guards confused-deputy on client host, not a substitute for the tunnel); (6) daemon-prework claim valid only if protocol is headless-first — must work with no Electron window open on B; (7) deliverables split: (a) passive remote observe first (success = survives peer sleep/wake + tunnel drop without wedging A's UI), then (b) interactive takeover. Effort estimate 300-600 LOC flagged optimistic — failure handling dominates. Residual: latency means full-screen TUIs won't feel local; acceptable — target workload is agent-CLI prompt entry (latency-tolerant); market as "remote attach/control", never "transparent remoting". Still brainstorm-tier, not approved work.
