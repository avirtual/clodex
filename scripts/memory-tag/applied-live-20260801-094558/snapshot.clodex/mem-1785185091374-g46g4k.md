RETIRED SETTLED POSITION #2 (was: "additionalContext survives /compact verbatim") — FALSE, measured 2026-07. Corrected: SessionStart additionalContext is RE-EMITTED after /compact because the CLI re-fires SessionStart with source=compact. It is SELF-HEALING, not preserved. The two are indistinguishable if you only check whether the string is present afterward, and completely different for any channel that does not re-fire. UserPromptSubmit does NOT re-fire, so anything delivered through it is summarized away like ordinary conversation content.

Evidence: pre-compact 196 messages / 396,080 bytes -> post-compact 4 messages / 121,748 bytes, body is [summary, assistant, user, system]. 119 probe strings sampled from pre-compact interiors: 14 survived, ALL inside the summary text (quoted by the summarizer, not carried over). Independently confirmed on my own seat: 32 SessionStart:compact events in one transcript, and my post-compact context carried the name-only hook line with NO memory digest.

COMPACT ECONOMICS (Bogdan's, correct): a compact discards the whole message array, so the bust is already paid in full. Refreshing the system prompt AT that boundary costs only the system block moving read->write; anywhere else it costs that plus the full array (111k-139k tokens). BUT /compact's own summarization request reads the entire pre-compact context as a cache READ — rewriting the prompt before it busts THAT too, making it strictly worse than doing nothing. The safe window is after the summarization returns, before the next turn is cached, which is exactly when SessionStart:compact fires. Gate: unknown whether the CLI re-reads --append-system-prompt-file without a respawn (t65 measures it).

SESSIONID: stable across all 40 compacts. /clear mints a new one; /compact is in-place. So JsonlWatcher onSessionId is a /clear-only detector and CANNOT see compact.
