PLUGIN DOCS — TWO ACCEPTED IMPROVEMENTS, queued AFTER unification alongside t31 (Bogdan, 2026-07-27; from an external AI review of plugins/README.md judged by "could an LLM build a correct plugin first try?"):

1. DENSE MACHINE-ORIENTED CHECKLIST near the TOP of docs/plugin-api.md (right after the TOC, not in the README — keeps the contract self-contained). ~30 lines: files required/optional, lifecycle order, capabilities, and CANNOTs. THE GAP IS REAL AND MEASURED: the three things an author must not get wrong sit at the END of a 1474-line doc — §10 lifecycle line 1189, §12 boundaries 1326, §13 not-exposed 1390 — while §4 host alone is ~300 lines. Anything reading top-down meets the full API surface long before the constraints. Restates nothing new; only reorders when it is learned.

2. SCAFFOLDER, NOT A SHIPPED TEMPLATE DIRECTORY. The review suggested plugins/TEMPLATE/. REJECT THAT SHAPE: discovery scans plugins/*/manifest.json and the DIRECTORY NAME IS THE ID, so a TEMPLATE dir becomes a phantom plugin row in Manage Plugins for every user, shipped inside app.asar where they cannot delete it. enabledByDefault:false does not help — the row still renders. DO INSTEAD: a command that copies git-branches into ~/.clodex/plugins/<id> and rewrites the manifest id. Also fixes the weakest step in the current path — "copy git-branches and GUT IT" asks an author to delete correctly, harder than filling blanks and the step most likely to leave a stray cache or settings section behind.

CAVEAT ON THE REVIEW ITSELF: it wrote engine.ts/renderer.ts. Clodex plugins are PLAIN .js, no TypeScript anywhere. It was synthesizing partly from priors, so weight its confidence accordingly — though its capabilities/cannot list did match §12/§13 correctly.
