Registry unification (the LAST step of the connection unification, deliberately sequenced after L1/L2/L3): the migration fork must be decided UP FRONT, before any code. Sixteen unlocked write sites across two processes over existing user data means the real hazard is a PARTIAL migration, not a wrong one — a half-written registry is worse than either shape.

Two options, and they want different tests:
1. Stop-the-world migration — one atomic conversion at launch, like legacy-sweep.js's marker-gated `run/.migrated`. Test: the conversion is idempotent and crash-safe mid-write.
2. Read-both / write-new transition — tolerant readers, gradual conversion. Test: OLD readers tolerate the NEW shape, which is a property to verify ON REAL BYTES rather than assume, since the old readers are the ones already shipped to users.

Option 2 only works if that tolerance holds; option 1 is simpler but needs the atomicity. Flagged by clodex-hand 2026-07-27 before the fork became implicit. Precedent to follow: legacy-sweep.js already did a name-driven, marker-gated one-shot migration successfully — read it first.

Related standing constraint: the peer store is RENDERER-written, so a raw `tunnel` argv must never become a peer-record field (DATA vs CODE partition — a persisted argv is a GUI-editable command line the app later executes).
