UNIFICATION — ONE REGISTRY (Bogdan, 2026-07-27). Completes the reach/use + ephemeral/persistent units:

MODEL: ONE LIST of remote Clodexes. Kind-distinctions become FLAGS on a row, not separate stores. Connected to a remote Clodex -> it is in the list. Is it a peer? row with peered flag set. Added as a clodexctl context? SAME list. Creating a new peer = PICK FROM THE LIST (or add new). Deletes both importers (~400 lines) and the duplicate-reconciliation pass, and kills `ctx import` refusing a cloud peer clodexctl itself deployed. Worth doing EVEN IF the underlying code is not shared.

THREE DECIDING CONSTRAINTS:

1. IDENTITY MUST COME FROM THE BOX, NOT THE REACH. Dedup on reach strings is unsolvable — the same box is `ssh box-7` to one client and a kubectl pod to another, and one box can legitimately be reachable both ways. The WIRE HELLO ALREADY CARRIES IDENTITY; dedup on that. A row is then ONE BOX WITH ONE OR MORE REACHES. Makes the picker honest: adding a peer to a box already present as a ctx entry ADDS A REACH to the existing row, not a new row needing later merge.

2. ONE LIST = ONE WRITER, BUT TODAY TWO PROCESSES WRITE. Clodex peer store is in userData, written FROM THE RENDERER; clodexctl writes contexts from the CLI. Merging needs a decided owner + atomic writes or CLI and GUI clobber each other. ~/.clodex/ is the natural home (both already own it, 0700) BUT this is a migration over existing user data — SCOPE IT SEPARATELY.

3. THE DATA/CODE PARTITION SURVIVES AND MATTERS MORE. The unified row still must NOT hold a raw `tunnel` argv as a field — a renderer-writable record the app later executes is a GUI-editable command line. Reach stays DECLARATIVE (kind + parameters); cli/src/transport.js builds argv from it. More important after merging, because the CLI now writes into that store too.
