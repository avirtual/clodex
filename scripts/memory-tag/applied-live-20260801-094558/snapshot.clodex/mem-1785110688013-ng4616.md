DECISION (mine, delegated authority, 2026-07-27) — port-forward --probe-http stays OPT-IN, not default-on.

t43's cloud finding: none of the four cloud templates (ssm/kubectl/gcloud/az) has any keepalive option and there is NO EQUIVALENT TO ADD — unlike ssh's ServerAlive, so it is not a parity gap. The real gap: `port-forward` WITHOUT --probe-http is a long-lived hold over a cloud transport with NO liveness signal at any layer. Documented from live use at cli/src/port-forward.js:71-80 — an SSM tunnel died silently during an instance OOM: local child alive, still accepting TCP, data channel gone.

RULING: do NOT arm the probe by default. `port-forward` is TRANSPORT-AGNOSTIC — the remote need not speak HTTP at all, so a default-on HTTP probe would declare a healthy non-HTTP forward dead. That is a worse failure than the one it fixes (a false death kills a working session; the current gap merely fails to notice a real death). `web` correctly always arms it because there the remote IS an HTTP GUI. This is a question about what port-forward may assume of its remote, and the answer is: nothing.

REVISIT IF: we ever learn the remote's protocol from the record (e.g. a registry row that knows the destination is a Clodex web port), at which point arming becomes derivable rather than assumed. Cheap TCP-connect probing is PERMANENTLY REJECTED — it reaches only the healthy local child and would report alive for the exact dead-data-channel case that motivated the probe (same reasoning as ServerAlive over SO_KEEPALIVE, one layer up; standing rule: a liveness signal that costs nothing to emit proves nothing about liveness).
