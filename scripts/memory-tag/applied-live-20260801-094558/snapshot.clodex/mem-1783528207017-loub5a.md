Clodex peering — settled design positions (2026-07-10, feature built + self-peer-verified, uncommitted; live state in memory.md): (1) Peering model is peer+stream, NOT ssh-remoting: the owner Clodex keeps full session ownership, the other side is a thin attach client via remote.js's protocol (/api/peer/hello, /api/attach SSE, token-gated /api/control|input|resize). SSH-as-terminal stays the free ad-hoc fallback. (2) No per-session "peerable" flag — host-level opt-in (remoteEnabled), tunnel = auth boundary, agent sessions only (bash stays private). (3) Read-only attach by default; typing/resize require explicit Take control (single-holder token, last-wins, auto-release on detach/stream-drop); passive viewing NEVER mutates owner state — owner geometry canonical, viewer letterboxes. (4) Replay = best-effort scrollback (256KB ring), reset-on-reconnect, never exact-terminal-state restoration. (5) Managed tunnels: Clodex spawns `ssh -N -L` itself (peer-tunnel.js); BatchMode=yes is a HARD line — key-based auth assumed, NO password-dialog proxying ever (passwords re-prompt on every reconnect, defeating unattended supervision; ssh-copy-id is less total friction). accept-new hostkeys (TOFU, changed key fails loudly). (6) Identity from hello-response content, never from localhost:port. (7) Offline peer = calm first-class state ("tunnel down"+stderr tooltip distinguishes misconfig from asleep). (8) Renderer seam = thin adapter only; all protocol/reconnect logic in main-process modules (peer-client.js/peer-tunnel.js — both DI-testable). Deferred phase 2: file-view content shipping, remote spawn, DM federation, peer-tab auto-reattach on restart.
