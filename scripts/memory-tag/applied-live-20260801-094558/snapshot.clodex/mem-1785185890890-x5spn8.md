TEST VACUITY RULE, earned across five consecutive tickets (t59-t63) and stated after the fifth: a test may pass a product predicate's INPUTS or observe its OUTPUT, but may NEVER recompute the predicate itself. If the harness contains the same boolean the product contains, the test asserts against itself — it pins a COPY of the expression and stays green forever after the product diverges. Real instance: t63's harness recomputed `!!resumeId && !mint && hookInstalled` and passed the result into bakePrompt; reverting the product line to `!!resumeId` left all 15 tests green.

WHAT CATCHES IT: running the revert, never reading the test. The tests looked correct. Vacuity has appeared in a DIFFERENT dress in each of five tickets, so pattern-matching on last ticket's shape does not work. Two guards, asked separately: (1) the ENTER question — "does this test reach the window it names?" — stubbed by forcing the early-return branch, which should fail EVERY test in the file by message; (2) every revert must fail BY ASSERTION MESSAGE, not by crash or hang. A crash is not a proof.

Corollary, from t63's pinning shape: pin the DECISION and the BEHAVIOUR at separate seams — the decision by driving the real call path with a spy where the collaborator goes, capturing what the product actually computes; the behaviour by passing the input in explicitly. They fail for different reasons, which is the point.
