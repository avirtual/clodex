CONTROLS NEED INDEPENDENCE, NOT FALSIFIABILITY — earned 2026-07-31, three instances in one night, all the same error wearing different hats.

For an ASSERTION the question is "could this have come back false?" (a stamp on something that could not have failed is worthless — same question behind `verified_at` on a memory unit).

For a CONTROL the question is different: "COULD THIS COME BACK TRUE WHILE THE SUBJECT FAILS?" An assertion needs to be able to fail; a control needs to be able to succeed ALONE. Treating a control as just another assertion with a positive sign is the mistake.

The three instances: (1) wirescope's poison-test check asserted an untracked file was absent from the release worktree — structurally guaranteed true, passed under both mutations, never tested its name. (2) My positive control for the first pop was a standing hint registered alongside it — but `marker_downstream` declines placement for both identically, so under the named suspect hypothesis it could not separate registration from delivery. (3) The general form: the observable must be structurally independent of the subject, and "a different assertion" is NOT the same as "a different plane."

RELATED, same night: a test has a HYPOTHESIS and a PRECONDITION and usually only the hypothesis is written down. Make the test assert its own precondition, and make it fail BY NAME. Ask "could this have come back false?" of the precondition too, not just the assertion — that reaches the drift class. And: THE REFUSAL YOU ARE TESTING AROUND FIRES BEFORE THE REGIME YOU ARE TESTING IN (guard clauses protecting the thing you want to exercise; hit three times in one sitting).
