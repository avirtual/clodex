VERDICT: hypothesis broadly right, true shape is THREE LAYERS not one module. EVERY divergence listed (supervision/retry, port stability, error sink, identity, auth) is a PARAMETER — none justifies two modules. What defeats a single unified object is THE STORE, not the connection.

SHAPE: L1 dial · L2 parameterised supervisor (params: retry x port x readiness x error-sink) · L3 one wire client with TWO consumer heads. All four existing supervision behaviours fall out of L2; withWire is the NULL CONFIGURATION, not a different thing. web-tunnel already IS peer-tunnel plus a deadline: Tunnel 101 nontrivial lines vs WebTunnel 141, 90 IDENTICAL, the 51 different lines exactly the four inversions its header declares.

PORT STABILITY IS CONSUMER-DERIVED, CONFIRMED IN CODE: peer-tunnel re-picks because a PeerConnection can be re-pointed via sync(); web-tunnel pins because a browser tab cannot. Both say so in prose at the call site (peer-wiring.js:196-202, web-tunnel.js:8-16), and openTransport ALREADY takes localPort=null as a parameter.

DUPLICATION BILL ~550 lines, ~250 deletable WITHOUT touching stores: three copies of one spawn-and-kill (peer-tunnel, web-tunnel, transport.js) incl. three copies of the process-group kill pid>0 guard and three copies of the ENOENT "is X installed and on PATH?" string; destination walk written 4x + 3 renderers ~168 lines; two SSE framings hand-rolled; importers peer-import.js 190/109 vs cli/src/import.js 217/156 exist ONLY because there are two stores.

SINGLE REGISTRY IS BIGGER THAN THE WORK IT ENABLES — sequence LAST and separately: peers has 6 write sites across renderer AND main (renderer.js:5287 whole-array replace, ipc-handlers x3, sandbox.js x2); contexts.json has 10, CLI-only. Both whole-file rewrites, NO LOCKING; safe today ONLY because they are different files. Security posture already equal (both -rw-------). ui-settings.json holds ~40 unrelated keys so the registry cannot be that file — needs a third file + migration merging two user-data files with dedupe-by-destination and token preservation + a locking rule + 15 write sites re-pointed.

RECOMMENDED ORDER: L1 + L3-plumbing first (cheap, independently verifiable, each closes a real defect) -> L2 next (biggest deletion, lowest design risk) -> registry last. NONE of L1-L3 depends on the registry: the two stores already reduce to the same reach shape and already share validateEntry (stores.js:305), so connection machinery can be unified ON TODAY'S RECORDS UNCHANGED.

CONSTRAINTS SURVIVE: all three spawn sites already build argv at spawn time from typed data (DATA/CODE partition unaffected); tokens header-only + renderer-stripped at ipc-handlers.js:1007; hostApi untouched (nothing in the connection path reads it).
