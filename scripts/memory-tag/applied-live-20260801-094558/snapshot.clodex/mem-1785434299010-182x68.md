Plugin settings live on the Manage Plugins row (t109, commit e2c2294), NOT in Preferences. Each plugin declaring rhost.ui.settings.section gets a Settings button on its row opening an inline panel with its own Save. Preferences renders no plugin sections at all — this was a MOVE, deliberately not a duplication, because two homes for one setting is the shape that survives review.

hostApi stays "1": the section spec (id/title/render/collect) is unchanged and no plugin source changed. Where the host MOUNTS a section is host policy, not surface.

renderer/plugin-host.js API: renderSectionsInto(pluginId, containerEl, values) and collectSectionsFrom(pluginId, containerEl). They take the container from the caller and must NEVER look up a fixed dialog id — two rows expanded at once is ordinary, and a document-wide lookup puts one plugin's form in another's panel. collectSectionsFrom returns null (not {}) when every section declines, so the caller skips settings.set instead of stamping an empty patch over stored values.

The inline panel is deliberately not a second overlay: #prefs-overlay and #plugins-overlay are siblings with no stacking manager.

Still untested by machine: the renderer.js wiring (makePluginSettingsPanel — button, toggle, save, collapse). renderPluginsDialog is not testable without extracting it. Manually verified in-app: button appears for git-branches, panel expands with real values, button disappears when the plugin is unchecked.
