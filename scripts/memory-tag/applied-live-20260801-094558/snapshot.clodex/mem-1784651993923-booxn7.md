GAP-AUDIT RESULT (docs/ipcmain-vs-wire-gap.md, 2026-07-21) — VERDICT (b): bounded enumerable convergence gap, NOT a structural fork. KEY NUANCE that reshapes the model: there are actually TWO wire surfaces, not one. (1) remote.js = the NARROW peering wire (owner/inbound half only) — what the daemon exposes today; covers ~a dozen core verbs sharing the EXACT same underlying engine fns as ipcMain (readSessionArgs/applySessionArgs, manager.create/kill, _deliverMessage) so it's provably not a divergent contract, just narrow. (2) web-host.js ALREADY implements the FULL 226-endpoint api-contract.js table — the SAME contract ipcMain speaks — as a second transport (WS), degrading the ~10 native-GUI seams to round-trips. So "is the full engine contract transportable off ipcMain?" is ALREADY ANSWERED YES by web-host; there's a single api-contract.js both ipcMain and web-host implement. The gap is only that the remote.js PEERING wire is narrow, not that the contract can't cross a wire. Real engine-capability gaps in remote.js = 14 groups ~90+ endpoints (session-lifecycle edges archive/retry/forget/export, team mgmt, SCM/worktree/file-explorer, library CRUD [read-only now], notifications, update-check, diagnostics, sandbox/docker lifecycle, workspace CRUD, global settings/theme, wirescope control, boiling-pot, mutating proxy cache-hold, and LARGEST: ~25 consumer-side peer-mgmt endpoints since remote.js is owner-only). GUI-host concerns (dialogs/menus/shell/window-anchoring) correctly ABSENT — proven cleanly degradable by web-host, not real gaps. IMPLICATION for daemoning: to drive a remote headless daemon with FULL fidelity, either (a) point a client at web-host's 226-endpoint contract (already complete, WS transport) rather than the narrow remote.js peering wire, OR (b) widen remote.js toward the enumerated 14 groups. web-host path likely the shortcut — it's the existence proof the whole engine contract already speaks over a wire. READ docs/ipcmain-vs-wire-gap.md for the endpoint-by-endpoint table.
