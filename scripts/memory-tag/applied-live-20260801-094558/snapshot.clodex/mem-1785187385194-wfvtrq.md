t69 ADDENDUM (dynamic system-prompt sections). Two things found after filing, both load-bearing for that ticket:

1. cli-hooks.js:59-62 claims "the protocol prompt ships via --append-system-prompt-file and is static, so the system-prompt bytes are IDENTICAL ACROSS AGENTS and share the provider prefix cache." That claim is FALSIFIABLE and t69 must test it: if the dynamic sections (cwd, env info, memory paths, git status) render into the system prompt, then two seats with different cwds have different system-prompt bytes and share NO prefix cache. Given that two code comments were already measured false this week (settled position #2, and the digest gate's justification), do not assume it holds.

2. THE STRONGEST ARGUMENT FOR THE FLAG, and it comes from the codebase itself: that same comment shows the design ALREADY makes this exact move deliberately — the per-agent NAME is routed through SessionStart additionalContext into the first user turn precisely to keep system-prompt bytes identical across agents ("the per-agent name rides this channel into the first user turn instead, where bytes diverge per session anyway"). --exclude-dynamic-system-prompt-sections applies the identical strategy to the machine-varying sections. So enabling it is not a new idea being imported; it COMPLETES a strategy this codebase already committed to and left half-done. Cite this in the t69 proposal.

Consequence for t70: if the sections DO churn, --system-prompt (which makes the flag a no-op) does not merely forfeit a nice-to-have — it re-breaks a cache property the codebase deliberately engineered for.
